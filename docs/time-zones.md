# Bot 时区

「设置 → Bot 工作设置 → Bot 工作默认时区」保存当前空间新计划的默认时区。个人空间和团队空间的拥有者可以修改，成员可以查看；当前产品统一使用账户登录，不提供旧单空间配对入口。它不改变电脑或浏览器的系统时区，也不是模型配置。

默认时区初始为 `Asia/Shanghai`。设置保存在独立的 SQLite 表中，读取不会创建配置记录。保存使用版本比较；另一窗口已修改时返回冲突，保留当前草稿供用户核对。等价时区名称规范化后不重复更新版本。账号空间请求使用固定账号身份核验，不能在切换账号后保存旧页面的选择。

网络中断后保留当前选择，可先「检查当前时区」。服务端仍是原版本且没有采用目标值时，可明确「重试原设置」；若另一窗口已保存不同值，则可「载入当前时区」或「保留选择并继续编辑」。检查发现当前值已经是目标，只确认当前状态，不推断原请求是否成功，也不自动重复提交。

## 默认值与已有任务

新建例行任务、首次设置主 Bot 每日跟进时，会把当时的空间默认时区保存到计划本身。之后修改默认时区，不改变已有计划的时区、下次时间或跟进设置版本。已有数据没有 `timeZone` 时，始终按 `Asia/Shanghai` 解释，不根据新的默认值或服务器所在时区猜测，也不在读取时补写数据。

每天、每周的例行任务和每日跟进可明确选择自己的时区。固定间隔任务按分钟执行，通常不显示时区选择；记录的时区用于时间展示，旧记录时区损坏时须明确修复。修改已有例行任务的时区会从当前时刻重新安排未来执行时间；仅改标题、提示词等不重排。旧客户端没有发送时区时，保留该任务原来的有效时区。重新开启暂停任务也从未来时刻安排，不补跑暂停期间的历史计划。

复制 Bot 或导入模板保留来源例行任务的时区，不采用接收空间的默认值。旧模板没有时区字段时仍按北京时间导入；旧模板的序列化和版本摘要不因读取而改变。导入者仍需明确选择保留启用状态或暂停例行任务。

## 日期与夏令时

每天、每周的执行日期和钟点按计划自身的 IANA 时区计算，周一到周日也采用当地日期。可使用 `Asia/Shanghai`、`America/New_York`、`UTC` 等有效名称；固定偏移字符串不是这项设置的时区标识。

夏令时开始使某个钟点不存在时，跳过该日期的执行机会，不悄悄移到另一钟点。夏令时结束使同一钟点出现两次时，只采用较早的一次；下一次执行计算不会选择当天第二次重复钟点。下一天按当地日历计算，不把每天简单当成固定 24 小时。间隔任务仍按真实经过的分钟数执行，不随夏令时缩短或拉长间隔。

现有例行任务的补跑行为保持原样：每日任务停机后可能补跑一次，再安排未来执行；每周任务已经跨过所属时区的到期日期时跳过，当天到期仍可等空闲后执行。维护锁期间不推进任务时间。手动执行可在任意日期发起，之后的下次时间仍按任务计划计算。因此，不能把所有例行任务描述为一律不补跑。

主 Bot 每日跟进使用独立的按当地日期和配置版本记录的领取日志。新配置不追补保存前的时刻；当天到期但暂忙时可稍后处理，过去日期不补发。已领取的机会在失败或重启后不自动重放，重启也不会重试结果不确定的模型请求。损坏的时间或时区设置显示错误，不让后台定时器异常退出。更多规则见[主 Bot](primary-bot.md)。

## 验证范围

领域测试覆盖默认配置的只读、授权撤回和版本边界，旧数据兼容，以及复制与模板导入的时区保留。主 Bot 与模板的既有本机 HTTP 回归也已通过。主 Bot 跟进通过本机合成模型服务走真实 Pi 调用，验证夏令时缺失钟点跳过、重复钟点只执行一次、重启去重和无效设置恢复。时间计算另有跨日、日期跳过及非整小时夏令时的受控测试。

这些结果不代表已经等待真实日历周期，也不等于本轮已完成产品界面的视觉或真实用户模型验收。
