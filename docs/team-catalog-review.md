# 智能组队中的 Bot 资料核对

生成方案之后，已有 Bot 的职责、长期指令或头像可能更新，也可能需要改用刚加入的 Bot。现在可以在原方案中选择「核对 Bot 资料」，查看所选现有 Bot 的最新名字、角色、简介、长期指令和头像，再明确选择「使用以上资料并保存草稿」。这一步保留目标、新 Bot 资料和成员分工，只更新方案使用的资料版本；不重新调用模型、不创建 Bot 或群聊、不开始任务。最终创建团队仍是单独一步。

资料预览标明「资料更新」「新加入」或「与方案一致」，仅包含当前选中的现有 Bot。新 Bot 的资料由用户在原表单中编辑，不需要重复核对。预览后修改草稿、成员或头像，或 Bot 来源发生变化，需要重新核对；不能用旧预览确认后来的内容。共享 Bot 不复制来源的账号、凭据、文件或记忆，来源已失效时不能被接纳为当前可用成员。

## 多个窗口与断线

保存以原方案版本和刚展示的资料为条件。另一个窗口已经修改、取消或创建团队时，旧确认会被拒绝；不能把已经创建的方案改回待确认，也不能因此再创建一个群。Bot 从空闲变成工作中的普通状态变化不影响资料版本；共享来源头像或配置更新会使旧资料失效。

资料保存有独立请求编号。断线后可以检查同一请求；原正文仍在当前页面时，也可以明确重试同一份内容。重复操作返回同一应用版本和方案当前状态，不覆盖后来编辑，更不会恢复已经取消的方案。界面会区分本次保存结果和之后发生的修改，保留当前编辑，要求用户核对后继续。

刷新页面只保留请求编号、方案编号和原版本，不在浏览器存储长期指令或草稿正文。若请求尚无回执，可明确继续编辑当前已保存的方案：先重新核对记录，再用版本检查使原请求不能迟到覆盖。如果本页仍保留原正文和草稿，结束核对后保留这些编辑；如果原正文已经丢失，则明确展示并使用服务端已保存的方案。查询不到回执本身不会自动重发或宣称未提交。

## 实现与验证边界

`BotTeamPlans.reviewBots` 生成只读资料预览。签名绑定方案、版本、规范化草稿、所选 Bot 及全部展示资料，签名密钥仅保存在当前空间数据库，不返回客户端。`refreshBots` 在同一 SQLite 写事务内复核原方案、当前资料和登录授权，更新草稿及已核对的目录版本，并写入 `bot_team_catalog_refreshes`。事务提交前再次复核共享来源，避免来源仅更新头像时旧目录仍被接受。未展示的 Bot 版本不会一起刷新。

普通草稿保存、最终确认和取消也把读取版本与写入放进同一事务，并在提交前再次检查权限。双数据库连接测试实证旧实现可以在竞争条件下重开已确认方案或重复建群；同一组测试验证修复后的行为。应用关闭在等待其他清理前就停止接纳方案变更。

当前空间拥有者可使用以下接口，固定账户请求头仍需匹配实际登录；普通成员和平台运营登录不能代替这一身份：

- `POST /api/workspaces/:workspaceId/bot-team-plans/:id/review-bots`：只读核对当前草稿的所选 Bot。
- `POST /api/workspaces/:workspaceId/bot-team-plans/:id/refresh-bots`：明确接纳本次核对并保存草稿。
- `GET /api/workspaces/:workspaceId/bot-team-plans/:id/catalog-refreshes/:requestId`：恢复原操作，返回应用版本与方案当前状态。

此功能补齐从目标、方案编辑到明确创建的工作流，参考入口与协作方向见 [Grok Bot 管理](https://docs.x.ai/grok-bot/bots)和[聊天协作](https://docs.x.ai/grok-bot/chat-and-collaboration)。资料核对的具体版本与恢复机制是本项目实现，不能据此声称与原产品内部架构相同。接口与 React 事件验证不能代替完整 GUI 验收；登录后的实际操作仍待临时测试账户创建审批。手动创建 Bot/群聊的未知响应恢复属于下一项独立工作。
