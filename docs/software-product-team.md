# Software product team and AI staff recruiter

The built-in **Software Product Team / 软件产品交付团队** creates a reviewable six-Bot plan. **AI Staff Recruiter / AI 同事招募员** helps identify missing AI responsibilities and proposes colleagues or a team using existing tools. It does not recruit or contact human candidates. Both entries are original bilingual catalog text; they do not install tools, grant access or start work when previewed.

## Start a product

1. Open **Bot library → Team templates → Software Product Team**, then load and edit the plan. Describe the real product, existing repository or workspace, intended users and the user journey that must work. Replace proposed members with suitable existing Bots to avoid duplicates.
2. Review the six responsibilities, keep the delivery lead selected, and confirm creation. The existing creation receipt makes a repeated confirmation return the same result.
3. Ask the lead in the created group to start. Address the lead rather than all members when the lead should coordinate dependent work. Provide the project location and the relevant authorized tools. Source editing without a usable command/browser environment does not establish that a product runs.
4. Review actual approvals when required. Follow the checkpoint if access, scope, cancellation or the delegation budget stops the run; request continuation in a new message after resolving the gap. Creating this team does not schedule background continuation.

For staffing, create the **AI Staff Recruiter** from the single-Bot catalog. Ask it to reuse existing colleagues and fill only missing responsibilities. It can propose one Bot with `propose_bot` when that tool is offered, or one team draft per root run with `propose_team`. You still review the normal card and confirm in the existing editor. A normal direct chat's `list_peers` may expose only that Bot; the recruiter must not treat that as proof that no reusable Bots exist. The smart-team planner has the broader workspace catalog, and the selected personal primary Bot can discover eligible local colleagues. The recruiter cannot appoint itself primary or silently change a group's membership.

## Phases and handoffs

| Phase              | Responsible Bot        | Required inputs                                         | Output and release condition                                                                                                                                      |
| ------------------ | ---------------------- | ------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1. Scope           | Software Delivery Lead | User goal, current project, available access            | Product brief and observable acceptance checklist; unresolved scope is visible.                                                                                   |
| 2. Design          | Product Architect      | Reviewed brief                                          | User journeys, UI states, architecture, data/API contract and acceptance-to-test map; lead checks consistency before implementation.                              |
| 3. Service         | Backend Engineer       | Reviewed design and API contract                        | Data model, API implementation, configuration needs and actual service-check evidence; contract differences are resolved before UI integration.                   |
| 4. Interface       | Frontend Engineer      | Design and actual backend handoff                       | Complete main journey, responsive/accessibility/error states and integration evidence; mock-only behavior remains explicitly unverified.                          |
| 5. Verification    | Product QA             | Exact implementation version and acceptance checklist   | Independent test report with commands or browser steps, outcomes and reproducible failures. Failed or blocked checks return to the lead.                          |
| 6. Delivery review | Delivery Reviewer      | Passing QA evidence and the same source/package version | Installation/run instructions, configuration examples, source/package inventory, dependency/asset notices and remaining gaps. Review does not deploy the product. |
| 7. Acceptance      | Software Delivery Lead | All handoffs and actual evidence                        | Reconcile every criterion, deliver accessible artifacts and state any unverified or blocked item.                                                                 |

A handoff states the goal, prerequisite artifact references, scope and file ownership, expected output and completion criteria. Its result states `ready`, `rework` or `blocked`, actual artifact locations and available hashes/versions, checks actually run, and unresolved issues. These are conventions in the assignment text, not new wire fields. A file on a paired computer must not be described as a registered workspace file without an actual transfer.

The lead waits for each `delegate` result and reads the referenced artifact when the returned excerpt is incomplete. One member writes a shared file at a time. For workspace edits, current hashes detect intervening changes. Test failures go back to the responsible implementer with the exact reproduction, followed by QA rechecking the affected behavior. The normal path uses five delegations, leaving at most three for rework or another focused review in the same run. If those are insufficient, the team saves a checkpoint rather than declaring completion.

A checkpoint records the project/version, accepted artifacts, current phase, unresolved failures, next owner and next action. This preserves evidence for a later run; it is not a durable job queue or an automatic restart mechanism.

## What the implementation actually supports

| Contract or runtime                                                                                                              | Implemented guarantee                                                                                                                                          | Limit                                                                                                                             |
| -------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| [`BotTeamDraft`](../shared/bot-team-plans.ts) and [Rust validation](../server/api/src/team_builder/draft.rs)                     | `title`, `summary`, `leadKey`, and 2–6 `members`; each member has an assignment and either a reusable ID or a new profile.                                     | There is no `dependsOn`, workflow graph or machine-enforced phase field.                                                          |
| [Team commit](../server/api/src/team_builder/mutations.rs)                                                                       | Atomically saves confirmed Bots, private chats, group and receipt. The selected lead is first, and `teamBrief` stores goal, summary, lead and assignments.     | Loading a plan does not create Bots; confirming it does not send a work request.                                                  |
| [Run context](../server/api/src/agent/runner.rs)                                                                                 | Supplies the saved team brief and eligible colleagues to the model; root tasks capture a group snapshot.                                                       | The runtime does not certify that a model followed every natural-language phase instruction.                                      |
| [`delegate`](../server/api/src/agent/delegation.rs)                                                                              | Waits for the child's real run/finalization and returns result identity, status and a bounded content excerpt. Current membership and authority are rechecked. | An excerpt can be truncated. Returned text alone is not proof of an artifact, passing test or customer acceptance.                |
| [Delegation family](../server/api/src/agent/delegation_family.rs)                                                                | At most eight delegated children per root, two active child slots and bounded nesting; cancellation and generation fences propagate.                           | This template uses sequential lead-to-member calls. It cannot turn a limit into unlimited autonomous work.                        |
| [Workspace tools](../server/api/src/agent/workspace_tools.rs)                                                                    | Reads/writes scoped files; edits may require the expected hash, and final file delivery requires the current hash.                                             | Code generation does not imply command execution. Local/remote computer actions need their existing capability and approval path. |
| [Bot proposals](../server/api/src/agent/creation_proposals.rs) and [team proposals](../server/api/src/team_builder/proposals.rs) | Real review cards, bound to the requesting account and run, use the current creation flows.                                                                    | A delegated child cannot create colleagues on its own. A proposal is not a completed hire or permission grant.                    |

The ordered workflow is implemented by the lead's tool calls and handoff review. It is **not** a server-enforced, persistent dependency graph. Permissions, membership, cancellation and mutation receipts are enforced by Rust; business acceptance is still a review step. See [team behavior and runtime guarantees](bot-settings-and-teams.md) for the existing collaboration model.

## Acceptance and verification

The catalog change is accepted when both languages appear in the existing Web/Flutter selectors, full instructions remain reviewable, the recruiter profile passes the normal profile validation, and the software team passes Rust's real draft and commit paths with all six assignments intact. Preview must cause no Bot creation or work; duplicate confirmation must reuse the original receipt. The dedicated `software_team_starter` integration test checks these server behaviors. Existing delegation tests exercise actual Pi child results and cancellation separately.

For a product produced with this team, acceptance needs evidence from that product: a runnable main journey, exact setup steps, test output for the delivered version, correct handling of the relevant failure cases, and an honest unverified-items list. A catalog test, a synthetic model response or successful team creation cannot establish that an arbitrary future product works. No external messages, provider calls, repository publication or deployment are part of these catalog checks.
